# R39 设计方案：账号 uid 403 时自动复位登录态（脱困修复）

## 现状取证（2026-08-29）
- 后端 main.py `guard_account_uid` 中间件：账号态 uid（u<id>，可枚举）读写必须带本人 Bearer token，否则 403「无权访问该账号数据，请重新登录」——安全上正确（防枚举他人数据）。
- 前端 api.js `rawRequest` 仅在 **401** 且 detail 含「未登录/登录已过期」时 clearAuth()（复位到匿名 uid）；**403 分支没有任何处理**。
- 卡死路径（R38 走查实测复现）：token 失效/被清但 anonUid 仍是账号 uid（u27）→ 所有 uid 读写（评论 liked 态、收藏、笔记、打卡、面试记录…）全部 403，且不会自愈——用户除非手动退出登录否则永久卡死。R38 生产走查中该状态触发了 console error。
- 触发面：服务端 token 过期/吊销、多端登录挤掉旧 token、storage 被部分清理，均是真实用户可达状态。

## 差距定级
P1（架构/健壮性）：安全守卫无前端脱困配套，真实用户可进入不可自愈的全站 403 状态。

## 方案（仅改 api.js rawRequest）
403 且 detail 含「无权访问该账号数据」时，与 401 过期同路径处理：clearAuth()（清 token/authUser、anonUid 复位回设备匿名 uid）+ toast「登录已过期，请重新登录」。下一次请求即以匿名 uid 正常读写，彻底脱困。不放宽后端守卫（枚举防护保持）。

## 不做
- 后端守卫语义变更；refresh token 机制（当前无此设计）。

## 验收
- build:h5 通过；生产复现卡死态（残留账号 uid+无 token）→ 首个 403 后自动复位，后续请求 200、console 不再持续 403；正常登录/游客流回归。
