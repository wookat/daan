# R94：/api/daily_set 冷路径预热——每日一练首跳不再吃 27s 长尾

日期：2026-08-31 · 状态：已实现

## 取证（生产一手证据）

1. R92/R93 部署（后端 rev 校验通过、容器 healthy）后实测：
   - `GET /api/daily_set` 冷请求 **27.05s / 200**（2026-08-31 10:4x UTC，容器重建后首次命中）。
2. 代码链路（backend/app/db.py `daily_set_ids`）：进程内 `_daily_set_cache` 按日缓存，但缓存只在**首个请求**时填充——每模块全量拉活跃题 id（合计 13 万+行）+ Python 端 md5 排序 ×5 模块；容器冷启动（部署重建/autoheal 重启）后该次请求在共享 2GB 宿主上实测 27s。
3. 边缘缓存（R69）TTL 仅 60s：冷窗口内首个真实用户直面 origin 27s；R83 的可靠投递救的是 submit，救不了「打开题组」这一跳。
4. 相关背景：R92 取证证明生产后端曾长期跑旧代码（`boot`/`login_nudge_*`/`stale_fallback`/`daily_set` 提交路径在旧后端上 400/404），`daily_set_entries=0` 的历史数据不能反推产品无人想用；本轮起后端版本可信，参与漏斗数据才开始有意义。

## 推断（与事实分开）

- 27s 属冷启动路径：缓存命中后同请求 <1s（R69 上线时实测）。宿主高负载会放大冷扫描耗时，但触发条件是「缓存空」。
- 每日一练是首页 hero 主推入口（R70/R77），冷 27s 直接打击的是最高意愿用户的第一跳。

## 方案（最小改动）

`main.py _warmup`（300s 周期，R64 既有线程）追加两行：

```python
db.daily_set_ids(db.cn_day())          # 今日题组 id 缓存常驻
db.daily_set_ids(<中国时区明日日期>)      # 预热明日：跨日 00:00 首个用户也不吃冷扫描
```

- 选题确定性（md5(day:qid)）使「预热明日」结果与明日实际一致；
- `_daily_set_cache` 上限 16 清空逻辑不变；
- 不动接口语义、不动边缘缓存 TTL、不加依赖。

## 验收

- 本地：ruff（既有 baseline 外无新增告警）、python -c 导入冒烟；
- 生产：部署重建容器后（缓存必然为空）等待一个 warmup 周期，`/api/daily_set` 首个外部请求 <2s；跨日边界靠确定性推断（明日预热同一代码路径，标注 untested：真实 00:00 边界）。

## 边界

- 共享宿主根因不变；warmup 本身在极端负载下也可能慢，但慢在后台线程而非用户请求。
- 60s 边缘 TTL 维持：participants 数需要相对新鲜。
