# R192：storm guard 将限速 429 计入错误窗口的跨端点封禁升级收口

## 一手取证

1. **旧标签页风暴复盘（探针流量，非真实用户）**：2026-09-01 11:27–18:37 origin 日志出现 ~57k 次
   `/api/exam/submit`、`/api/exam/report/*?uid=r176chk` 404（~210 次/分钟，单 IP 140.232.64.5 =
   本开发机）。溯源为本机 Chrome 遗留的旧 exam 标签页（R181 修复前的 bundle 常驻内存，自动交卷
   失败无限重试），已定位并关闭。期间 502×~2k 为同 IP 过载症状。
2. **为何当时零 429**：风暴时段生产容器运行的是 R182 守卫部署前的旧镜像（容器 19:14 才重建）。
   守卫本身逻辑无缺陷——修复部署后实测同端点 30×404 后第 31 次起 429，行为正确。
3. **新 verified 缺陷（本轮修复）**：生产实测连续触发 `/api/report` 的 rl() 限速拿到 35 个 429 后，
   **无关端点** `GET /api/exam/report/999999`（应 404）也全部返回 429——rl() 的 429 响应被
   storm guard `record()` 按「≥400 即错误」计入窗口，35≥30 触发该 IP 全 /api 封禁。
   与 R182 设计注释「429 不计入窗口」矛盾（当时只豁免了守卫自身的 429 早退路径）。

## 影响面

- 单端点限速（如 alog 120/h、report 20/h）被升级为整 IP 全 API 60s 滚动封禁；
- NAT 共享出口下一个客户端打满某个 rl 桶，会连坐同出口所有用户的全部 API；
- 前端离线队列每次重试吃 429 也会累积错误计数，延长封禁。

## 方案（最小修改）

`storm_guard.record()` 排除 429：`if status < 400 or status == 429 or not ip: return`。

论证：429 本身就是已被限速的廉价响应（rl/守卫均为内存判断，不落线程池/SQLite），风暴防护的
目标是拦截高成本错误重试风暴；对 429 再叠加全 IP 封禁没有额外保护收益，只放大误伤半径。
rl 桶按端点/身份精细限速的语义保持不变。

## 验证

- 本地：vitest 不涉及；pytest 新增用例（429 不计数、404 仍计数封禁）+ 存量全绿；ruff 通过。
- 生产：部署后先触发 /api/report rl 限速至 429，再请求无关端点确认不再连坐（404 正常返回）。

## 如实局限

- 风暴复盘属探针流量，无真实用户受损证据；
- 守卫/rl 均为内存态，重启清零（既有已知局限，不变）。
