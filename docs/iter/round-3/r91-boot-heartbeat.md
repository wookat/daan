# R91：boot 版本心跳——回答「存量客户端到底跑什么版本」

## 取证（2026-08-29，生产）

1. **每日一练 0 真实参与**：daily_set_entries 全表 0 行（唯一一条 submit 实为本机部署探针，已清理）。
   但产品并非无人用：近 2 天 answer_log 有 17 个真实 uid、160+ 条作答。
2. **归因困境**：R67/R71 两轮陈旧壳自愈上线后，无法度量「存量客户端版本分布」——
   slow_load 只在慢载时上报（近 3 天 49 条中真实用户样本均无 `;v:` 戳，但这是幸存者偏差：
   旧 bundle 不带 v 字段，快载客户端根本不上报）。
   每日一练入口（R70 首页 hero）只存在于新 bundle；若活跃用户大多困在旧壳，0 参与就是投放面问题而非产品力问题。
3. 现有事件无一能做「活跃客户端 × 版本」的分母：heatmap_view/share_open 等都是特定行为埋点。

## 方案（最小闭环）

- 前端 main.js（H5）：load 后 6s 上报一次 `boot` 事件，`ref = v:<主chunk hash>;sw:<0/1>`；
  以 localStorage `kg_boot_day` 按中国时区日期节流——**每客户端每天至多 1 条**（活跃 uid ~20/天，量级可忽略）。
- 后端 team.py：track 白名单加 `boot`（入库侧沿用现有 ua/hs 追加逻辑，不改）。
- 不加接口、不改 UI、不采集新隐私字段（hash 是公开资源文件名）。

## 判定用途

- v 分布 = 当前 bundle 占比 → 直接验证 R67/R71 自愈链路对存量客户端的真实效果；
- boot 日活 uid 数 = 每日一练漏斗分母 → 区分「没人看到入口」vs「看到不想点」；
- 后续每轮发版后可量化收敛速度。

## 边界

- 仅 H5；boot 上报失败静默（trackEvent 已 catch）。
- 不回填历史；结论需等真实样本落库（下一轮取证消费）。
